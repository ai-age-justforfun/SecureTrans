# Backlog 推演假设与验证标准（PMF 前哨）

> 版本：v1.0 | 日期：2026-09-14 | 阶段：PSF 收尾 → PMF 前哨
> 定位：ADR-027 第 2/3 条的落地清单——把 PSF 期间的"推演需求"（想多了、回退、搁置）显式标记为**假设**，每条附验证标准；**证据成立才进当前迭代，否则不实现**。
> 状态定义：`parked` 搁置（有触发条件）/ `open` 待验证 / `validated` 已成立 / `abandoned` 当前放弃（PMF 后按需重估）

## C. 商业 / 市场假设（PSF→PMF，来自 docs/04 §2.2.2）

| # | 假设 | 验证指标 | 数据来源 | 成功阈值 |
|---|------|---------|---------|---------|

| C2 | 摆渡场景是高频痛点 | 每周提交单数 | 审计日志 | ≥ 10 单/周（当前日均 5-10 次访问基线） |

| C4 | 免审批/审批流使用比例合理 | 免审批通过 vs 人工审批比例 | 审计日志 | 免审批占比 < 80%（否则审批形同虚设） |

## 使用规则（与 ADR-027 一致）

1. **证据优先**：任何假设进入当前迭代前，必须满足其"验证标准"列——不因"想得完整"而实现。
2. **状态流转**：本清单每轮 Sprint 复盘时刷新一次状态；validated 的条目转需求（进 PRD/Story），abandoned 的条目留档不删除（回退=信息）。
3. **与 docs/04 的关系**：docs/04 是 PMF 阶段流程与总体指标；本清单是"从 PSF 带来的待验证假设"明细，PMF 启动时逐条核销。

## D. 技术债与遗留（v2.7.6 立账）

| # | 项 | 影响 | 偿还触发 |
|---|----|------|---------|
| D1 | 生产容器内代码为热更新（基础镜像 `v2.7.3-feishu-r1`） | 镜像与运行代码不一致，人工重建容器易漏参数 | 本版 tag 发布后由 CD 重建镜像（一次性偿还） |
| D2 | `.env RESET_PASSWORD` 与 admin 实际密码需保持一致 | 不一致时 CD 冒烟登录失败→发布假红 | 已对齐为统一管理密码；后续改密同步 `.env` |
| D3 | 通知里的"部门负责人"只提示不点名（`leader_user_id` 未使用） | 审批人可能不清楚找谁 | 出现漏批/重复批反馈 |
| D4 | 外网下载列表按提交人过滤（有意设计） | 接收方本人无法看到别人摆渡给他的文件 | 业务确需接收方下载时再改为接收方视角（L2） |
| D5 | `/api/health` 回显 `resetPassword` | 初始密码可被读取（仅内网面） | 安全审计要求收敛时移除（L1） |
| D6 | `approved` 长期未下载单依赖有效期归档 | 存储缓慢增长 | 观察期后核对 11 单历史待下载单的归档情况 |
| D7 | **Release 缺 `image.tar.gz` 离线镜像资产**（Gitea runner 已退役，镜像改 GitHub 云端构建推 GHCR） | 生产零出网无法 pull GHCR，离线部署只能继续用旧镜像 + 热更代码（当前 v2.7.6 即此形态） | GitHub `release.yml` 在已有 `docker build` 之后追加 `docker save | gzip` 并 `gh release upload image.tar.gz`；生产 `podman load`（L1，需跑一次 tag 验证） |
