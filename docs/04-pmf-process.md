# SecureTrans PMF 标准流程文档

> 版本：v1.0 | 日期：2026-08-26 | 阶段：PMF（Product-Market Fit，产品-市场匹配验证）
>
> 核心理念：**Lean 定方向、Agile 做迭代、DevOps 保交付，三者联动，业务优先，轻量落地**

---

## 1. PMF 阶段目标与定位

### 1.1 什么是 PMF
PMF（Product-Market Fit）验证：确认产品**在真实环境中被目标市场持续使用**，且用户愿意为它付费/深度依赖。从 PSF 的"原型验证"走向 PMF 的"真实部署验证"。

### 1.2 PSF → PMF 的区别

| 维度 | PSF 阶段 | PMF 阶段 |
|------|---------|---------|
| 验证对象 | 原型（模拟数据） | 真实系统（真实文件/网络/AD） |
| 部署方式 | 本地静态页面 | 服务器部署（内网+NAS） |
| 用户范围 | 3-5 人体验 | 1-2 个试点部门/客户，10-50 人真实使用 |
| 数据 | localStorage 模拟 | SQLite/真实数据库，真实文件 |
| 核心指标 | 用户反馈、场景认可 | 活跃度、留存率、审批时效、文件量 |
| 质量要求 | 核心流程可用 | 生产级稳定、安全合规 |

### 1.3 PMF 阶段成功标准
- ✅ 至少 1 个试点部门/客户真实部署并持续使用 4 周以上
- ✅ 周活跃用户率 > 60%（试点用户中每周至少使用 1 次）
- ✅ 核心流程（提交→审批→摆渡→下载）端到端成功率 > 95%
- ✅ 平均审批时效 < 24 小时
- ✅ 无 P0 安全事故和数据丢失
- ✅ 至少 1 个客户明确表示愿意付费/扩大使用范围

### 1.4 PMF 阶段交付物
| 交付物 | 说明 |
|--------|------|
| 可部署系统 | 轻量后端 + 前端，单服务器部署包 |
| 部署手册 | 安装、配置、AD对接、NAS挂载步骤 |
| 运维手册 | 日常运维、备份、故障排查、升级 |
| 用户手册 | 各角色操作指南 |
| 试点报告 | 部署数据、用户反馈、问题清单、PMF结论 |

## 2. Lean-Agile-DevOps 联动方法论

### 2.1 三者定位与联动

```
┌─────────────────────────────────────────────────────┐
│                    Lean（精益）                        │
│  做什么？→ 验证假设、数据驱动、小批量试错              │
│  输出：优先级排序的需求 Backlog、验证指标              │
└──────────────────────┬──────────────────────────────┘
                       │ 需求输入
                       ▼
┌─────────────────────────────────────────────────────┐
│                   Agile（敏捷）                        │
│  怎么做？→ Sprint 迭代、Story 拆分、快速交付          │
│  输出：可工作的软件增量、验收通过的功能                │
└──────────────────────┬──────────────────────────────┘
                       │ 代码提交
                       ▼
┌─────────────────────────────────────────────────────┐
│                  DevOps（开发运维）                    │
│  怎么交付？→ CI/CD、自动化测试、监控、快速回滚         │
│  输出：稳定部署的生产环境、运行数据、反馈闭环           │
└──────────────────────┬──────────────────────────────┘
                       │ 运行数据/用户反馈
                       ▼
              回到 Lean（调整优先级）
```

**联动核心**：Lean 用数据告诉 Agile "做什么"，Agile 把功能交给 DevOps "安全交付"，DevOps 的运行数据反馈给 Lean "下一步做什么"。

### 2.2 Lean（精益）在 PMF 阶段的应用

#### 2.2.1 精益创业循环（Build-Measure-Learn）
```
建立假设 → 构建最小功能 → 部署测量 → 数据分析 → 学习决策 → 调整假设
```

#### 2.2.2 PMF 阶段关键假设与验证指标

| 假设 | 验证指标 | 数据来源 | 成功阈值 |
|------|---------|---------|---------|
| 用户确实需要跨网审批摆渡 | 周活跃用户率 | 系统日志 | > 60% |
| 审批流能提升效率 | 平均审批时效 | 审批记录 | < 24h |
| 零拷贝摆渡满足性能 | 摆渡操作耗时 | 系统日志 | < 5s |
| 用户愿意持续使用 | 4周留存率 | 用户活跃度 | > 50% |
| 管理员能独立运维 | 运维问题工单量 | 支持记录 | < 1次/周 |

#### 2.2.3 小批量部署策略
- **第 1 批**：IT 部门内部 3-5 人，验证部署和基础功能（1 周）
- **第 2 批**：1 个业务部门 10-20 人，验证真实业务场景（2 周）
- **第 3 批**：扩大到 2-3 个部门或 1 个外部客户，验证规模化（4 周）
- 每批结束后复盘，决定是否扩大、调整、或暂停

### 2.3 Agile（敏捷）在 PMF 阶段的应用

#### 2.3.1 Sprint 节奏（2 周）
PMF 阶段功能更复杂，Sprint 延长到 2 周：
- 周一：Sprint Planning（1 小时）
- 每日：Daily Standup（15 分钟，站会）
- 第二周周四：代码冻结，开始测试
- 第二周周五：Sprint Review + Retrospective + 发布

#### 2.3.2 Story 拆分（延续 PSF 方法）
- 沿用 PSF 的 Story 模板和 INVEST 原则
- PMF 阶段新增技术 Story 和运维 Story：
  - 技术 Story：如"AD 认证集成""文件上传断点续传"
  - 运维 Story：如"日志轮转配置""备份脚本""监控告警"

#### 2.3.3 优先级框架（RICE + 业务优先）
PMF 阶段需求增多，用 RICE 简化版排序：
- **Reach（影响人数）**：多少用户用到
- **Impact（影响程度）**：对核心指标影响多大
- **Confidence（信心）**：我们有多确定这个需求有效
- **Effort（工作量）**：需要多少人天

公式：`优先级分 = (Reach × Impact × Confidence) / Effort`

**业务优先原则**：当技术债/优化和业务功能冲突时，优先业务功能，技术债排入专门的"技术债 Sprint"（每 4 个 Sprint 安排 1 个）。

### 2.4 DevOps 在 PMF 阶段的应用

#### 2.4.1 轻量 CI/CD 流水线
PMF 阶段不追求复杂工具链，用最轻量的方式实现自动化：

```
代码提交(Git) → 自动测试(pytest) → 构建打包 → 部署测试环境 → 人工验收 → 部署生产
```

**工具选择（轻量级）**：
- CI：GitHub Actions / GitLab CI / 本地脚本（三选一）
- 测试：pytest（后端）+ 手动前端测试
- 部署：脚本 + systemd 服务，蓝绿部署（两个目录切换）
- 配置：环境变量 + .env 文件

#### 2.4.2 发布策略
- **发布频率**：每 2 周 1 次（Sprint 结束），紧急 Bug 修复随时发布
- **发布流程**：
  1. 开发完成 → 测试环境部署 → 回归测试
  2. PO 验收通过 → 准备发布包
  3. 备份生产环境（数据库+配置）
  4. 部署生产（蓝绿切换，5 分钟内完成）
  5. 冒烟测试（核心流程走一遍）
  6. 发布完成，通知用户
- **回滚**：蓝绿部署，出问题 1 分钟切回旧版本

#### 2.4.3 监控与告警
PMF 阶段监控轻量化，关注核心指标：
- **系统监控**：CPU/内存/磁盘/NAS 空间（脚本定时检查，超阈值发邮件/飞书）
- **应用监控**：接口响应时间、错误率（日志分析）
- **业务监控**：日提交量、待审批积压量、摆渡成功率
- **告警方式**：飞书机器人推送（简单直接）
- **日志**：按天轮转，保留 30 天，关键操作永久归档

## 4. 质量体系（PMF 阶段）

### 4.1 质量策略升级
PMF 阶段是真实环境，质量要求比 PSF 高：
- **核心流程零 Bug**：提交/审批/摆渡/下载必须 100% 稳定
- **安全合规**：密码加密、传输加密、权限隔离、审计完整
- **数据安全**：文件不丢失、归档完整、备份可恢复
- **性能达标**：单文件 10GB 可上传，摆渡 < 5s，页面响应 < 2s

### 4.2 四层质量保障

#### 第一层：单元测试（Developer）
- 后端核心逻辑必须有单元测试：MD5 计算、特征码匹配、免审批判定、权限校验
- 覆盖率目标：核心模块 > 70%
- 工具：pytest，CI 自动运行

#### 第二层：集成测试（Developer + PO）
- API 接口测试：提交、审批、摆渡、下载、用户管理
- 端到端测试：完整业务流程走查
- 多角色权限测试：确认越权访问被拒绝
- AD 集成测试：本地用户/AD用户登录、角色映射

#### 第三层：验收测试（PO）
- 对照 Story 验收标准逐条验证
- 真实场景模拟：用真实文件、真实 AD 账号测试
- 兼容性测试：Chrome/Edge/Firefox

#### 第四层：试点用户验证（真实用户）
- 试点用户真实使用，收集反馈
- 观察实际使用中的问题和卡点
- 定期（每周）收集用户满意度

### 4.3 安全质量要求
PMF 阶段必须满足的安全基线：
- ✅ 密码 bcrypt 哈希存储，不明文存储
- ✅ HTTPS 传输（部署时配置 Nginx SSL）
- ✅ 权限隔离：普通用户无法访问管理功能
- ✅ 操作审计：所有关键操作（登录、提交、审批、配置变更）记录日志
- ✅ 文件完整性：上传后 MD5 校验，下载时再次校验
- ✅ 备份机制：数据库每日备份，归档文件由 NAS 保障
- ✅ 会话管理：登录 Session 24h 过期，退出立即失效

### 4.4 Bug 管理（PMF 升级）
| 级别 | 定义 | 响应时间 | 修复时间 |
|------|------|---------|---------|
| P0 阻断 | 核心流程不可用/数据丢失/安全漏洞 | 立即（30min内） | 4 小时内 |
| P1 严重 | 重要功能异常，有 workaround | 2 小时内 | 24 小时内 |
| P2 一般 | 边缘功能/UI 问题 | 下个 Sprint | 下个 Sprint |
| P3 优化 | 体验优化/建议 | 排入 Backlog | 按需 |

P0/P1 Bug 紧急发布流程：修复 → 测试 → 直接部署生产（不走正常 Sprint 发布节奏）。

### 4.5 Definition of Done（PMF 版）
一个 Story 算"完成"：
- ✅ 代码开发完成，Code Review 通过
- ✅ 单元测试通过，核心逻辑有测试覆盖
- ✅ 集成测试通过，端到端流程跑通
- ✅ PO 验收通过
- ✅ 无 P0/P1 Bug
- ✅ 相关文档更新（用户手册/运维手册）
- ✅ 部署脚本/配置更新（如需要）
- ✅ 监控/告警配置（如需要）

## 5. PMF 阶段关键流程

### 5.1 部署流程（首次部署）
```
环境准备 → NAS挂载 → AD对接配置 → 系统安装 → 初始化配置 → 数据导入 → 测试验证 → 上线
```

详细步骤见《部署手册》，关键节点：
1. 服务器环境检查（OS、Python、磁盘、网络）
2. NAS 挂载测试（读写权限、软链接支持）
3. AD 连接测试（认证、用户查询、组查询）
4. 系统安装（后端服务、前端静态文件、Nginx 配置）
5. 初始化（admin 账号、特征码规则、审批人配置）
6. 冒烟测试（提交→审批→摆渡→下载全流程）
7. 用户培训 + 上线通知

### 5.2 迭代发布流程（每 2 周）
```
Sprint Planning → 开发 → 单元测试 → 代码冻结 → 集成测试 → PO验收 → 发布准备
    → 备份生产 → 蓝绿部署 → 冒烟测试 → 发布通知 → 监控观察
```

### 5.3 运维流程（日常）
- **每日**：检查系统状态、磁盘空间、待审批积压
- **每周**：备份验证、日志清理、用户反馈整理
- **每月**：安全补丁更新、性能复盘、数据归档清理
- **每季度**：全面备份恢复演练、安全审计

### 5.4 用户反馈闭环
```
用户反馈（飞书群/工单） → 分类（Bug/需求/咨询） → 评估优先级
    → Bug: 按级别修复 → 需求: 进入 Backlog, RICE 排序 → 咨询: 直接回复
    → 每周 Review 反馈趋势 → 调整产品方向
```

## 6. 度量与指标体系

### 6.1 北极星指标
**周活跃审批完成数**：每周有多少个提交单完成了完整的审批→摆渡→下载流程。这个指标直接反映产品是否被真实使用。

### 6.2 核心指标看板

| 类别 | 指标 | 目标值 | 统计频率 |
|------|------|--------|---------|
| 用户活跃 | 周活跃用户率 | > 60% | 每周 |
| 用户活跃 | 4 周留存率 | > 50% | 每月 |
| 业务效率 | 平均审批时效 | < 24h | 每周 |
| 业务效率 | 待审批积压量 | < 10 单 | 每日 |
| 系统稳定 | 核心流程成功率 | > 95% | 每周 |
| 系统稳定 | 系统可用性 | > 99% | 每月 |
| 系统性能 | 平均摆渡耗时 | < 5s | 每周 |
| 质量 | P0/P1 Bug 数 | < 2 个/月 | 每月 |
| 运维 | 平均故障恢复时间 | < 30min | 每月 |

### 6.3 指标采集方式
- 系统日志自动统计（Python 脚本分析日志，生成周报）
- 数据库直接查询（提交量、审批量、用户活跃度）
- 飞书机器人每周一自动推送上周指标到项目群

## 7. 风险与应对

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| AD 对接复杂，部署受阻 | 延期 | 中 | 提前在测试环境验证 AD 对接，准备本地用户 fallback 方案 |
| NAS 软链接权限问题 | 摆渡失败 | 中 | 部署前充分测试 NAS 软链接，准备硬链接/复制 fallback |
| 试点用户积极性不高 | 数据不足 | 中 | 选有真实痛点的部门，IT 部门带头用，定期跟进 |
| 安全审计不通过 | 无法上线 | 低 | 提前对照安全基线自查，邀请安全部门提前评审 |
| 性能不达标（大文件） | 用户体验差 | 中 | 提前做 10GB 文件上传测试，优化分片上传 |
| 单人开发精力不足 | 进度延迟 | 高 | 严格控制范围，P2 需求一律延后，考虑外包非核心模块 |

## 8. PMF 验收决策流程

PMF 阶段结束时（通常 8-12 周），组织正式验收：

### 8.1 验收检查清单
- [ ] 北极星指标连续 4 周达标
- [ ] 核心指标全部达到成功阈值
- [ ] 试点用户满意度调查 > 4 分（5 分制）
- [ ] 至少 1 个客户/部门明确表示愿意扩大使用/付费
- [ ] 无未解决的 P0/P1 Bug
- [ ] 部署手册、运维手册、用户手册完成
- [ ] 运维流程跑通，管理员能独立处理常见问题

### 8.2 决策选项
1. **PMF 达成，进入规模化**：产品被市场验证，开始扩大客户范围，考虑商业化
2. **PMF 基本达成，需优化**：核心验证通过，但有明确改进点，再迭代 1-2 个 Sprint 优化
3. **PMF 未达成，调整方向**：关键指标不达标，用户留存低，回到 PSF 重新验证需求
4. **PMF 未达成，暂停**：市场反馈负面，考虑放弃或重大转型

## 9. 从 PMF 到规模化的过渡建议

PMF 验证通过后，进入规模化阶段时建议：
- **技术**：考虑从 SQLite 迁移到 PostgreSQL，单服务器扩展到双机热备
- **安全**：引入杀毒引擎、DLP 内容检测，通过等保测评
- **功能**：三员分立（系统管理员/安全管理员/审计管理员）、大文件断点续传、多语言
- **商业**：定价策略、销售流程、客户成功体系
- **流程**：从 2 周 Sprint 过渡到持续交付，DevOps 体系完善
