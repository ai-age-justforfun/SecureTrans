## 1. 产品概述

### 1.1 产品定位
SecureTrans 是一款面向中小企业的轻量级单向跨网文件审批摆渡系统，解决内网红区/黄区到外网绿区的文件安全外发问题。核心价值：**审批可控、摆渡0拷贝、归档可审计**。

### 1.2 目标规模（v1.4 确认）
| 维度 | 指标 |
|------|------|
| 注册用户 | ≤ 50 人 |
| 并发用户 | 2-3 人 |
| 日均申请量 | 3-5 单 |
| 文件大小 | 大多数 1-20MB，偶尔 300-500MB |
| 部署方式 | 单服务器 + 本地/NAS 存储 |

### 1.3 核心设计原则
- **轻量级**：单服务器部署，Flask + SQLite，无复杂中间件
- **0拷贝摆渡**：os.rename 同文件系统移动（只改目录项，不移动数据块）
- **AD 优先**：AD 作为身份源，本地只存角色映射
- **审计完整**：所有操作留痕 SQLite，归档文件永久保留
- **够用就好**：支撑到 200 人规模不改架构

## 2. 系统架构（v1.4 重大调整）

### 2.1 部署架构
```
┌─────────────────────────────────────────────────────┐
│              单台服务器（双网卡）                      │
│  eth0(内网) ◄───►  Flask Web应用  ◄───► eth1(外网)  │
│                   │                                   │
│                   ▼                                   │
│  ┌──────────────────────────────────────────────┐   │
│  │  /nas/  (本地磁盘或NAS挂载，单文件系统)        │   │
│  │  ├── staging/    ← 刚上传，待审核              │   │
│  │  │   └── {提交单ID}/                           │   │
│  │  │       ├── files/                            │   │
│  │  │       └── manifest.json                     │   │
│  │  ├── external/   ← 审核通过，可外网下载         │   │
│  │  │   └── {提交单ID}/ → os.rename from staging  │   │
│  │  └── archive/    ← 过期/驳回，永久归档          │   │
│  │      └── {提交单ID}/ → os.rename from external │   │
│  └──────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

### 2.1b 单网卡部署模式（v2.0 新增）

**双网卡隔离是部署架构层面的事，不是应用层功能**。应用层（Flask）不感知网卡数量，只识别网段。v2.0 起支持两种网络模式，按实际部署选择：

| 模式 | NETWORK_MODE | 网络接入 | 内外网识别 | 隔离效果 |
|------|-------------|---------|-----------|---------|
| **双网卡**（默认，原设计） | `dual` | eth0 内网 + eth1 外网 | Nginx 双 server 注入 `X-Network-Zone` | 物理隔离 |
| **单网卡**（v2.0 新增） | `single` | 一个网卡，防火墙放行内外网访问同一网址 | 应用层按客户端 IP 网段（`INTERNAL_CIDRS`）识别 | 逻辑隔离（网段识别） |

**单网卡要点：**
- 防火墙（如 FortiGate）放行内外网网段访问同一网卡地址，应用通过 `INTERNAL_CIDRS` 网段判定内/外网。
- 内外网各自功能、内外网应用完全隔离逻辑不变：外网面仅开放登录+下载，管理接口一律 403（`before_request` 强制兜底）。
- 网页随用户所在网段自动识别：内网用户见完整菜单，外网用户仅见外网下载；无权限菜单灰显/隐藏。
- 127.0.0.1/::1 loopback 恒判为内网管理面（健康检查、本机管理不受网段误判影响）。
- `NETWORK_MODE` 由 `.env` 配置，切换仅改配置不改代码。

### 2.2 os.rename 0拷贝移动原理（v1.4 核心）

**为什么 os.rename 是 0 拷贝？**
在同一个文件系统内，`os.rename()` 是原子操作，**只修改目录项（directory entry），不移动任何数据块**。文件内容在磁盘上的物理位置完全不变，只是路径变了。因此：
- 移动 1KB 文件和移动 500MB 文件，耗时相同（毫秒级）
- 不占用额外磁盘空间
- 原子操作，不会出现半移动状态

**与软链接方案对比：**

| 维度 | 软链接方案（v1.3） | os.rename 方案（v1.4） |
|------|-------------------|----------------------|
| 摆渡操作 | 创建 symlink | os.rename 目录 |
| 数据拷贝 | 0 | 0（同文件系统内） |
| 速度 | 毫秒级 | 毫秒级 |
| 跨平台 | Windows 兼容性差，需管理员权限 | 全平台原生支持 |
| NAS 兼容性 | 部分 SMB/NFS 挂载不支持 symlink | 所有支持 rename 的文件系统 |
| 权限复杂度 | 软链接权限和目标文件权限分离，易混乱 | 文件权限不变，简单 |
| 归档位置 | archive 是唯一真实存储，external 是链接 | 文件随状态移动，最终到 archive |
| 适用场景 | 复杂企业级 | 初创公司轻量级 |

**结论**：os.rename 方案在 0 拷贝性能上与软链接等价，但可靠性、兼容性、可维护性远优于软链接，非常适合初创公司。

### 2.3 文件生命周期与状态流转

```
┌──────────┐   上传    ┌──────────┐  审核通过  ┌──────────┐  外网下载  ┌──────────┐
│  用户提交 │ ───────► │ staging/ │ ─────────► │external/ │ ─────────► │ 下载记录 │
│          │           │ pending  │  os.rename │ approved │  流式读取  │downloaded│
└──────────┘           └────┬─────┘            └────┬─────┘            └────┬─────┘
                             │ 审核驳回                 │ 过期清理                │
                             │ os.rename                │ os.rename (Cron半夜)    │
                             ▼                          ▼                          │
                        ┌──────────┐            ┌──────────┐                     │
                        │ archive/ │            │ archive/ │                     │
                        │ rejected │            │ archived │                     │
                        └──────────┘            └──────────┘                     │
                             │                                                    │
                             └────────────────────────────────────────────────────┘
                                          所有文件最终归档保留
```

**状态定义：**

| 状态 | 物理位置 | 说明 |
|------|---------|------|
| pending | /nas/staging/{id}/ | 刚上传，待审核 |
| approved | /nas/external/{id}/ | 审核通过，可外网下载 |
| rejected | /nas/archive/{id}/ | 审核驳回，归档保留 |
| downloaded | /nas/external/{id}/ | 已被下载（记录下载时间，文件仍在external） |
| archived | /nas/archive/{id}/ | 过期清理，永久归档 |

**关键操作：**
1. **上传**：文件写入 `/nas/staging/{提交单ID}/files/`，计算 MD5，生成 manifest.json
2. **审核通过**：`os.rename(/nas/staging/{id}/, /nas/external/{id}/)` → 0拷贝，瞬间完成
3. **审核驳回**：`os.rename(/nas/staging/{id}/, /nas/archive/{id}/)` → 直接归档
4. **外网下载**：从 `/nas/external/{id}/files/` 流式读取，记录下载时间，物理文件不动
5. **过期清理**：定时任务（Cron）半夜执行，`os.rename(/nas/external/{id}/, /nas/archive/{id}/)` → 0拷贝归档

### 2.4 提交单唯一标识
- 提交单 ID = `UUID前8位` + `_` + `yyyyMMddHHmmss` 时间戳
- 示例：`a3f2c1d8_20260826143022`
- 保证目录名全局唯一，os.rename 无冲突

## 3. 技术架构（v1.4 调整）

### 3.1 技术栈

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| 运行环境 | **Python 3.12 + venv（--copies）** | 与系统 Python 完全隔离，独立运行与发布（见 3.1b） |
| Web框架 | **Flask 3.x** | 轻量级，生态成熟，适合小团队 |
| 认证 | **Flask-Login** | 会话管理，本地用户+AD用户统一接入 |
| 数据库 | **SQLite** | 单文件，零配置，支撑 50 人绰绰有余 |
| 文件存储 | 本地磁盘 / NAS 挂载 | 单文件系统，确保 os.rename 0拷贝 |
| 大文件上传 | Flask + Werkzeug 流式 | 配置 MAX_CONTENT_LENGTH，直接 save 到磁盘 |
| 定时任务 | **APScheduler** 或系统 Cron | 过期文件清理，半夜执行 |
| 反向代理 | Nginx | 负载均衡、HTTPS、大文件上传缓冲 |
| 进程管理 | systemd (Linux) / 计划任务 (Windows) | 开机自启、崩溃重启 |

### 3.1b venv 部署环境隔离（v2.1 新增）

**要求：应用运行环境与服务器系统环境完全隔离，可独立运行与发布。**

- 部署必须创建独立 venv：`python3.12 -m venv --copies venv`；应用与依赖全部安装在 venv 内，不写入系统环境。
- `--copies` 为复制解释器（非符号链接）：venv 内 python3 是独立可执行文件，系统 Python 升级/移动/卸载不影响应用；应用卸载也不影响系统。
- 依赖安装进 venv（`venv/bin/pip install --no-index --find-links wheelhouse`），不碰系统 site-packages。
- 启动与进程管理（gunicorn / waitress / systemd）一律使用 venv 内解释器路径（如 `venv/bin/gunicorn`、`venv/Scripts/python.exe`）。
- 版本一致性：venv 内 Python 必须为 3.12（与离线 wheel 的 cp312 匹配）；部署脚本创建后自动校验版本，不匹配告警并提示重建。
- 双平台强制：Linux `deploy.sh` 与 Windows `deploy.ps1` 均执行 `--copies` 创建 + venv 内版本校验。

### 3.2 为什么选 Flask 而不是 FastAPI
- Flask 生态更成熟，Flask-Login 等插件稳定
- 团队学习成本低，文档丰富
- 50 人规模、2-3 并发，性能完全不是瓶颈
- 异步特性（FastAPI 优势）在这个场景用不上
- 部署更简单，无需 ASGI 服务器

### 3.3 大文件上传处理（500MB 极限）

**配置：**
```python
app.config['MAX_CONTENT_LENGTH'] = 1 * 1024 * 1024 * 1024  # 1GB 上限
```

**原理：**
- Werkzeug 的 `request.files['file'].save(path)` 自动流式写入磁盘，不会把整个文件读入内存
- 500MB 文件上传时，内存占用稳定在几 MB
- Nginx 反向代理需配置 `client_max_body_size 1G`

**优化建议：**
- 上传时实时计算 MD5（流式读取，不二次读盘）
- 上传完成后校验文件大小
- 超大文件（>500MB）提示用户建议拆分或使用其他方式

## 4. 核心业务流程

### 4.1 完整流程
```
上传提交(staging) → 文件清单+MD5 → 免审批判定 → 分级审批 → os.rename摆渡(external) → 外网下载 → 过期os.rename归档(archive)
```

### 4.2 免审批规则
免审批自动通过需**同时满足两个条件**：
1. **免审批功能开关已开启**
2. **提交单内所有文件均匹配特征码规则**（只要有一个不匹配，就不能免审批）

**特征码规则可配置（三要素）：**
- 文件类别（扩展名白名单）
- 文件名（正则匹配）
- 二进制特征（文件头魔数）

### 4.3 分级审批
| 接收方类型 | 审批层级 | 审批人 | 摆渡动作 |
|-----------|---------|--------|---------|
| 合作方 | 一级 | 部门主管 | 通过后 os.rename → external |
| 非合作方 | 二级 | 部门主管 → 公司高管 | 二级通过后 os.rename → external |
| 免审批通过 | 零级 | 自动通过 | 立即 os.rename → external |
| 任何驳回 | - | - | os.rename → archive（rejected状态） |

**审批层级规则（语义B：同人跨级自动跳过）**：
- 非合作方提交单一级审批通过后，若当前一级审批人**同时具备二级审批权限**（如二级审批人被配置为一级审批人），则自动跳过二级审批，直接 os.rename 摆渡到 external
- 判断依据：`can_approve_level(2)` 对当前审批人为真（角色或 approvers 表任一通道）
- 审计链补充：跳过时写入一条 level=2 自动跳过记录，保证审批链可追溯
- 典型场景：小团队中同一人（如负责人）既是一级又是二级审批人，避免同人对同一提交单重复审批
- **纯固定规则，无配置开关**：PMF 阶段若客户需要恢复"强制两级把关"，再引入开关

## 5. 用户与身份管理

### 5.1 身份架构：AD 优先 + 本地补充
- **AD 作为唯一身份源**：用户账号、密码、姓名、部门、在职状态都在 AD
- **本地不复制 AD 用户**：只存角色映射表（哪个AD用户/AD组 → 什么角色）
- **本地用户表仅存**：admin（初始管理员）+ 极少数测试账号
- AD 用户入职/离职/调岗 → AD 组变化 → 角色自动变化，本地零维护

### 5.2 权限模型（简化方案）

> **设计原则**：借鉴 Windows Server 的"本地超级用户"模型——只有 admin 一个超级权限入口，
> 其余用户默认都是普通用户，**不给普通用户角色提权能力**（不设复杂 role/group 体系）。

| 权限主体 | 权限 | 配置方式 |
|---------|------|---------|
| **admin** | 全部权限：用户管理、系统配置、特征码规则、合作方白名单、**审批人配置**、审计、归档 | 固定初始账号，仅此一个管理入口 |
| **普通用户**（默认所有用户） | 提交文件、查看自己的提交、下载 | 无需配置 |
| **审批人**（一级/二级） | 审批对应层级的提交单 | 由 **admin 在审批人配置中指定**（approvers 表），不依赖角色提权 |

**规则**：
- 所有新用户默认普通用户，无提权能力，无法自行配置任何权限
- 审批权限通过 `approvers` 表配置（admin 维护），配置后该用户即可审批对应层级
- 管理配置（用户/系统/特征码/合作方/审批人）**仅 admin 可操作**，后端 `@role_required("admin")` 强制校验
- 保留 `dept-manager`/`executive` 角色字段仅作向后兼容，正式权限判定以 approvers 表为准
  （`can_approve_level()` 双通道：角色 OR approvers 表，任一满足即可审批）

### 5.3 登录方式
- **默认自动探测**：先查本地用户表，匹配则本地认证；不匹配则走 AD
- **显式指定 AD**：输入 `域\用户名` 或 `用户名@域` 格式
- 本地 admin 固定账号名，永远走本地认证

## 8. 架构决策记录（ADR）

### ADR-001：为什么用 os.rename 而不是软链接
- **日期**：2026-08-26
- **背景**：v1.3 设计使用软链接（symlink）实现零拷贝摆渡，但存在跨平台兼容性和 NAS 支持问题
- **决策**：改用 os.rename 同文件系统移动
- **理由**：
  1. os.rename 在同文件系统内是 0 拷贝（只改目录项），性能与软链接等价
  2. 全平台原生支持，无需特殊权限
  3. 所有文件系统（包括 SMB/NFS 挂载）都支持 rename
  4. 文件权限不变，没有软链接的权限分离问题
  5. 代码更简单，维护成本更低
- **后果**：文件物理位置随状态变化（staging → external → archive），但因为是 rename 所以 0 拷贝

### ADR-002：为什么用 Flask 而不是 FastAPI
- **日期**：2026-08-26
- **决策**：使用 Flask + Flask-Login
- **理由**：
  1. Flask-Login 生态成熟，认证方案稳定
  2. 团队学习成本低
  3. 50 人规模性能不是瓶颈
  4. 部署简单（WSGI，gunicorn/waitress）

## 9. 本期逻辑调整（2026-08-28 落地，v1.5 变更记录）

> 测试同步更新至 143 项 100% 通过（见 docs/06-test-report.md）。

### 9.1 有效期统一由系统配置控制
- **变更**：提交表单不再显示/输入"有效期（天）"；提交接口忽略前端传入的 `expiryDays`。
- **生效**：有效期唯一设置点为 **系统管理 → 系统配置 → 默认有效期（天）**（默认 7 天），所有提交单统一使用该值。
- **原因**：有效期是系统级策略，不应由提交人在单个提交单上指定，避免口径不一致。

### 9.2 接收方字段调整
- 接收方新增 **单位（必选）**，提交单缺少单位时拒绝创建（400）。
- 接收方姓名、单位必填；邮箱可选（PMF 后按需决定是否必选）。
- 接收方类型选"合作方"时，前端展示已配置合作方下拉；若清单为空或用户自定义，可手动填写，**提交时自动加入合作方清单**（当前信任模式，PMF 后视需要收紧为仅 admin 可配置）。

### 9.3 合作方管理（恢复配置管理 + 使能开关）
- 新增"合作方管理"菜单（admin-only）：列表 / 新增 / 使能 / 删除。
- `partners` 表新增 `enabled` 字段；**禁用后不参与白名单自动判定**（is_partner 仅匹配 enabled=1），也不出现在提交表单合作方下拉。

### 9.4 用户使能开关
- `local_users` 表新增 `enabled` 字段；**禁用后无法登录**（登录校验 status='active' 且 enabled=1）。
- 新增用户默认使能（测试期）；生产版本可改为默认禁用，由管理员逐个启用。
- **admin 永久使能，不可禁用**（admin 为系统内置首个/末个用户，禁用会锁死系统入口）。

### 9.5 特征码规则默认禁用（模板化 + 安全兜底）
- 内置特征码规则（PDF/Word/压缩包/Vivado 等 20 条）作为**模板，默认全部禁用（enabled=0）**，由管理员按需启用。
- **安全策略**：免审批总开关开启时，若没有启用的特征码规则 → 无文件可匹配 → 所有提交走人工审批（默认保守）。只有管理员显式启用规则后，匹配文件才可免审批。
- 自动化回归测试前置会临时启用所有规则以便跑通免审批场景；生产环境按需启用。

### 9.6 角色体系收窄（纯 approvers 表配置审批权）
- **不设 role 体系**：角色仅 `admin`（系统管理员，内置唯一）与 `internal-user`（普通用户）。移除 dept-manager/executive 等审批角色。
- **审批权限纯由 approvers 表配置**：`can_approve_level` 只认 admin + approvers 表；普通用户被配置为一级/二级审批人后即可审批（前端"待我审批"菜单同步显示）。
- 创建本地用户固定为普通用户（忽略角色参数）；AD 角色映射仅允许 admin/internal-user，非法角色返回 400。

### 9.7 仪表盘 admin-only（管理视图移到最后）
- 仪表盘展示全局运营统计（今日提交/待审批/免审批率/文件总数等），**仅 admin 可见**，菜单移至最末。
- 后端 `/api/stats` 增加 `role_required("admin")` 强制校验（普通用户直接调 API 返回 403）。
- 普通用户登录默认进入"文件提交"页；admin 默认进入仪表盘。

### 9.7b 外网面（下载面）菜单收敛
- 外网面（X-Network-Zone: external）**仅显示"外网下载"菜单**，隐藏其余全部菜单（含文件提交/我的提交/审批/管理），防止从网外看到或触发上传申请等内网功能。

### 9.8 审计日志统计 Tab

### 10.1 单网卡部署支持（NETWORK_MODE）
- 双网卡隔离是部署架构层面的事（Nginx 绑定内外网卡），应用层不涉及双网卡。
- 新增**单网卡模式**：防火墙放行内外网访问同一网卡地址，应用按客户端 IP 网段（`INTERNAL_CIDRS`）识别内外网；内外网功能与隔离逻辑与双网卡完全一致。
- 双网卡模式保留，`NETWORK_MODE` 配置切换（dual/single），实际部署按现状选择。

### 10.2 双操作系统支持
- 支持 **Windows**（waitress）与 **Linux**（gunicorn）双平台部署。
- 必要支持库/venv 由部署脚本自动获取；服务器断网场景支持离线包预下载打包（`offline-deps` / `offline-deps-win`），安装说明与脚本保留在部署文档。

### 10.3 版本号单一来源
- 系统版本号收敛为**单一常量**（`app.py APP_VERSION`），前端显示读取该值，无多处重复定义。

### 10.4 部署文档统一
- 测试/生产/双OS/网络隔离等部署文档合并为唯一 `docs/DEPLOY.md`（原 runbook 并入）。

### 10.5 Rocky Linux 一键式部署
- 上传部署包 + 指定版本 python3（3.12）离线包放同一目录即可一键部署（`bash infra/deploy.sh`）。
- Python 3.12 获取三级优先：①系统已有 3.10+ 直接用；②`offline-python/*.rpm` 离线安装（`get-offline-python.sh` 联网生成）；③在线 dnf（需防火墙临时放行 80/443 访问华为云/阿里云/Rocky 镜像源）。
- 离线依赖优先（`pip --no-index --find-links`），完全离线无需放行网络。

### 10.6 Windows 部署同等完善（方案 B）
- `infra/deploy.ps1` 与 Linux 同等一键式：Python 获取（系统/内置 exe/URL）→ venv → 离线 wheel → .env → 启动验证。
