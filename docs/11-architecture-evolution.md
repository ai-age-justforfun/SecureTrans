# SecureTrans 架构演进与选型设计

> 版本 1.0 | 2026-09-08
> 定位：补充架构设计说明，覆盖 Web 框架选型（Flask/FastAPI）、Nginx 组合、企业成长各阶段的架构演进路线与技术断裂点判断；与 README 的 ADR-002（Flask 决策）配套。

## 一、Flask vs FastAPI：功能与性能对比

| 维度 | Flask 3.x | FastAPI |
|------|-----------|---------|
| 定位 | 微框架（同步 WSGI） | 现代 API 框架（异步 ASGI） |
| 请求模型 | 同步，线程池（每请求一线程） | 异步事件循环（单线程高并发 IO） |
| 性能（IO 密集） | 受线程数限制，单机约数百 QPS | 高并发显著更强，单机约数千 QPS |
| 性能（CPU 密集） | 无本质差异（需多进程/任务队列） | 无本质差异（需多进程/任务队列） |
| 数据校验 | 手写校验 / Flask-WTF | Pydantic 自动校验 + 类型提示 |
| API 文档 | 无自动生成 | OpenAPI/Swagger 自动生成 |
| 生态 | 极成熟（Flask-Login/Admin/SQLAlchemy） | 成长中（FastAPI-Users 等） |
| 学习成本 | 低 | 中（需理解 async/await） |

**结论**：Flask 赢在生态成熟 + 简单；FastAPI 赢在高并发 IO + 自动文档。
选型依据不是"谁更好"，而是"瓶颈在哪"——本项目 PSF 阶段选 Flask（ADR-002），瓶颈不在并发。

## 二、Nginx 的定位：反向代理层

| 能力 | 说明 |
|------|------|
| 反向代理 | 内/外网入口，转发给 Gunicorn/Uvicorn |
| TLS/HTTPS 终结 | 证书管理、HTTP/2 |
| 大文件上传 | client_max_body_size（本项目默认 800MB） |
| 静态资源 | 直接服务，不经 Python |
| 负载均衡 | 多 worker/多实例轮询 |
| 网络隔离 | 双网卡注入 X-Network-Zone 头（本项目） |

**Nginx 不提供业务能力**——它是"入口开关面板"。Gunicorn/Uvicorn 才是真正的应用服务器。

## 三、典型组合矩阵

| 组合 | 架构 | 适用场景 | 性能量级 |
|------|------|---------|---------|
| A. Flask 单体（内置服务器） | 单进程单线程 | 开发/测试/内部工具 | 约 50 QPS |
| B. Flask + Gunicorn（本项目当前） | 多 worker WSGI | 小规模生产 | 约数百 QPS |
| C. Flask/FastAPI + Gunicorn/Uvicorn + Nginx | 标准三层 | 中小规模正式部署 | 约千 QPS |
| D. FastAPI + Uvicorn + Nginx + Redis/MQ | 异步 + 缓存/队列 | 高并发 API 服务 | 约数千 QPS |
| E. 微服务 + API 网关 + K8s | 分布式 | 大型组织/云原生 | 弹性扩展 |

## 四、演进路线：创业 → 中小 → 大型（业务连续性）

业务连续性 = 可用性 × 扩展性 × 可维护性。每个阶段只解决当前最痛的问题，不提前引入复杂度。

| 阶段 | 架构形态 | 核心目标 | 典型规模 |
|------|---------|---------|---------|
| P0 创业（PSF/PMF） | 单体 + SQLite（本项目现状） | 快速验证、跑通流程 | 1 服务器，<100 用户 |
| P1 早期增长 | + PostgreSQL + Gunicorn + Nginx | 数据可靠、稳定服务 | 1-2 服务器，数百用户 |
| P2 中型 | + Redis 缓存 + 多实例 + 负载均衡 | 响应速度、横向扩展 | 3-10 服务器，数千用户 |
| P3 规模化 | 服务拆分 + 异步任务（FastAPI 局部引入） | 团队并行、业务解耦 | 10+ 服务器/容器 |
| P4 大型 | 微服务 + K8s + GitOps | 弹性、多团队自治 | 云原生 |

## 五、技术断裂点：不连续演进的颠覆式创新判断

**断裂点 = 旧技术范式无法满足新约束的时刻**。

| 断裂类型 | 信号 | 迁移方向 |
|---------|------|---------|
| 并发断裂 | 同步阻塞成为瓶颈 | Flask → FastAPI/ASGI |
| 数据断裂 | 单库写放大 | SQLite → PostgreSQL → 读写分离/分片 |
| 状态断裂 | 内存会话无法多实例 | 会话外部化（Redis/DB） |
| 组织断裂 | 单团队无法并行（康威定律） | 模块 → 服务拆分 |
| 交付断裂 | 部署频率受限 | 容器 → K8s → GitOps |
| 范式断裂（颠覆式） | 技术栈整体被更优范式替代 | 如 AI 时代：规则/人工 → LLM Agent |

**颠覆式创新关键过程**（低端切入 → 改进 → 替代）：
1. 新范式先在"边缘/低端"场景跑通（本项目的 PSF 阶段正是如此）
2. 成本/效率曲线快速追赶旧范式
3. 当新范式在主流场景性能追平旧范式时，即"颠覆时刻"——此时应主动迁移而非守旧

**每季度复盘判断清单**：
- [ ] 当前架构哪个指标最先到极限（并发/数据/团队/交付）？
- [ ] 该瓶颈是否值得提前投入（而非等痛了再动）？
- [ ] 有没有更低成本的新范式在边缘场景出现？
- [ ] 现有技术栈还有多少"可复用存量"？

## 六、本项目现状与下一步

- **现状**：组合 B（Flask + Gunicorn），单机 + SQLite，测试/生产一个开关切换，PSF 阶段
- **下一步（PMF 前）**：保持组合 B；不提前引入 PostgreSQL/Nginx
- **触发升级的硬信号**：真实用户并发 >50、正式数据可靠性要求、多实例 HA 需求 → 升级组合 C（+ Nginx + PostgreSQL）
