# SecureTrans PSF 标准流程文档

> 版本：v1.0 | 日期：2026-08-26 | 阶段：PSF（Problem-Solution Fit，问题-方案匹配验证）
>
> 核心理念：**业务优先、轻量敏捷、快速闭环、验证驱动**

---

## 1. PSF 阶段目标与定位

### 1.1 什么是 PSF
PSF（Problem-Solution Fit）验证：确认我们做的东西**确实解决了目标用户的真实问题**，且解决方案被用户认可。

### 1.2 PSF 阶段成功标准
- ✅ 核心业务流程（提交→审批→摆渡→下载）被用户认可
- ✅ 关键角色（普通用户/审批人/管理员）的核心场景跑通
- ✅ 至少 3 个潜在客户/内部用户完成原型体验并给出反馈
- ✅ 需求优先级明确，PMF 阶段范围确定
- ❌ 不要求：生产级安全、高性能、高可用、完整功能

### 1.3 PSF 阶段交付物
| 交付物 | 说明 | 状态 |
|--------|------|------|
| PRD | 产品需求文档，含业界对标、架构设计 | ✅ v1.3 |
| MVP 原型 | 可交互的单页 Web 原型，localStorage 模拟数据 | ✅ v2.0 |
| 用户验证记录 | 客户/内部用户体验反馈、问题清单 | 📝 进行中 |
| PSF 验收报告 | 验证结论、PMF 阶段需求优先级 | 🔜 待输出 |

## 2. Agile 方法论（轻量化 Scrum）

### 2.1 为什么用轻量化 Scrum
PSF 阶段团队小（1-3 人）、需求变化快、交付周期短，采用**轻量化 Scrum**，去掉重型仪式，保留核心闭环。

### 2.2 角色定义（一人多角）
| 角色 | 职责 | 建议人选 |
|------|------|---------|
| Product Owner (PO) | 需求优先级、Story 验收、业务决策 | 金涛 |
| Scrum Master | 流程推进、障碍清除、节奏把控 | 金涛（兼任） |
| Developer | 设计、开发、测试、部署 | 开发人员 |
| 用户代表 | 需求验证、反馈提供 | 潜在客户/内部用户 |

### 2.3 Sprint 节奏
- **Sprint 长度**：1 周（PSF 阶段快速迭代）
- **每周循环**：
  - 周一上午：Sprint Planning（30 分钟，确定本周 Story）
  - 每日：Daily Standup（10 分钟，异步文字即可）
  - 周五下午：Sprint Review + Retrospective（1 小时）

### 2.4 核心仪式（极简版）
| 仪式 | 时长 | 目的 | 产出 |
|------|------|------|------|
| Sprint Planning | 30min | 确定本周交付的 Story | Sprint Backlog |
| Daily Standup | 10min | 同步进度、识别障碍 | 进度更新 |
| Sprint Review | 30min | 演示本周成果、收集反馈 | 反馈清单 |
| Retrospective | 30min | 复盘流程、持续改进 | 改进项 |

## 3. Story 划分与验收标准

### 3.1 Story 划分原则
- **INVEST 原则**：Independent（独立）、Negotiable（可协商）、Valuable（有价值）、Estimable（可估算）、Small（小）、Testable（可测试）
- **一个 Story = 一个用户场景的完整闭环**，不拆成"做前端""做后端"这种技术任务
- **Story 大小**：单个 Story 应在 1-3 天内完成，超过则拆分

### 3.2 Story 模板
```
作为 [角色]，我希望 [功能]，以便 [业务价值]。

验收标准：
1. [具体可验证的行为1]
2. [具体可验证的行为2]
3. [具体可验证的行为3]

优先级：P0/P1/P2
估算：XS/S/M/L
```

### 3.3 SecureTrans PSF 阶段 Story 清单（示例）

| ID | Story | 优先级 | 状态 |
|----|-------|--------|------|
| ST-001 | 作为普通用户，我可以上传文件并自动生成文件清单和MD5，以便提交外发申请 | P0 | ✅ |
| ST-002 | 作为普通用户，我可以看到免审批预判结果，以便知道是否需要等待审批 | P0 | ✅ |
| ST-003 | 作为部门主管，我可以看到待我审批的申请并进行通过/驳回操作 | P0 | ✅ |
| ST-004 | 作为公司高管，我可以对非合作方文件进行二级审批 | P0 | ✅ |
| ST-005 | 作为外网用户，我可以下载已摆渡完成的文件 | P0 | ✅ |
| ST-006 | 作为管理员，我可以配置特征码规则和免审批开关 | P1 | ✅ |
| ST-007 | 作为管理员，我可以配置合作方白名单和审批人 | P1 | ✅ |
| ST-008 | 作为管理员，我可以查看审计日志和归档检索 | P1 | ✅ |
| ST-009 | 作为管理员，我可以管理本地用户和AD角色映射 | P1 | ✅ |
| ST-010 | 作为用户，我可以通过本地账号或AD账号登录系统 | P0 | ✅ |
| ST-011 | 作为管理员，我可以配置AD连接参数并测试连接 | P2 | ✅ |
| ST-012 | 作为用户，我可以看到文件摆渡的完整流程状态和时间线 | P1 | ✅ |

### 3.4 优先级定义
- **P0**：核心流程，没有就无法验证 PSF
- **P1**：重要功能，影响用户体验和完整度
- **P2**：锦上添花，时间允许才做

### 3.5 Story 验收流程
1. Developer 完成开发后**自测**（对照验收标准逐条验证）
2. 自测通过 → 提交 PO 验收
3. PO 验收通过 → Story 关闭，标记 ✅
4. PO 验收不通过 → 退回，注明问题，Developer 修复

## 5. 质量体系

### 5.1 PSF 阶段质量策略
PSF 阶段**不追求完美质量**，但要保证核心流程稳定可用。质量策略：
- **核心流程零 Bug**：提交→审批→摆渡→下载主流程必须稳定
- **非核心功能可降级**：边缘场景有 Bug 不影响 PSF 验证，记录即可
- **快速修复 > 完美预防**：发现问题快速修复，不过度设计

### 5.2 三层质量保障

#### 第一层：Developer 自测（必做）
- 对照 Story 验收标准逐条验证
- 核心流程走查：提交一个申请 → 审批 → 摆渡 → 下载，全流程跑通
- 多角色验证：用不同角色账号登录，确认权限隔离正确
- 边界测试：空输入、超长输入、特殊字符

#### 第二层：PO 验收（必做）
- PO 以真实用户视角操作，不看代码只看效果
- 验收标准逐条确认
- 记录体验问题和改进建议

#### 第三层：用户验证（PSF 核心）
- 邀请潜在客户/内部用户体验原型
- 观察用户操作，记录卡点和困惑
- 收集反馈：哪些有用、哪些多余、哪些缺失
- 输出用户验证记录

### 5.3 Bug 管理
- Bug 分级：
  - **P0（阻断）**：核心流程无法进行，立即修复
  - **P1（严重）**：重要功能异常，当天修复
  - **P2（一般）**：边缘场景/UI 问题，排入下个 Sprint
- Bug 记录在飞书任务/多维表格，含：复现步骤、预期结果、实际结果、截图、优先级

### 5.4 定义 of Done（DoD）
一个 Story 算"完成"，必须满足：
- ✅ 代码开发完成
- ✅ Developer 自测通过（对照验收标准）
- ✅ PO 验收通过
- ✅ 无 P0/P1 Bug
- ✅ 相关文档更新（PRD/操作手册）

## 6. PSF 阶段关键流程

### 6.1 需求→开发→验收 闭环
```
需求提出 → Story 拆分 → 优先级排序 → Sprint 规划
    ↑                                            ↓
用户反馈 ← Sprint Review ← 测试验收 ← 开发自测
```

### 6.2 用户验证流程
1. **准备**：确定验证目标、准备原型、准备引导问题
2. **邀请**：联系 3-5 个潜在用户/内部用户
3. **执行**：
   - 5 分钟介绍背景
   - 15 分钟用户自由操作（观察，不引导）
   - 10 分钟访谈（感受、问题、建议）
4. **总结**：整理反馈、分类（需求确认/新需求/Bug/体验优化）、更新 Story 优先级
5. **迭代**：高优先级反馈进入下一个 Sprint

### 6.3 PSF 验收决策流程
PSF 阶段结束时，PO 组织验收会议：
1. 回顾所有 Story 完成情况
2. 回顾用户验证反馈
3. 回答三个问题：
   - 问题是否真实存在？（用户确实有这个痛点吗？）
   - 方案是否被认可？（用户愿意用吗？）
   - 是否值得进入 PMF？（有明确的客户/场景愿意付费/深度使用吗？）
4. 决策：
   - **进入 PMF**：核心验证通过，确定 PMF 范围
   - **继续 PSF**：有关键问题未验证，再迭代 1-2 个 Sprint
   - **调整方向**：需求理解有偏差，调整 PRD 后重新验证

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 用户反馈不足 | 无法验证 PSF | 内部用户先行，再拓展外部客户 |
| 需求蔓延 | Sprint 无法交付 | 严格优先级，P2 一律延后 |
| 技术方案不确定 | 开发阻塞 | PSF 阶段用原型模拟，PMF 再验证技术 |
| 角色一人多角精力不足 | 进度延迟 | 缩小 Sprint 范围，聚焦 P0 |

## 8. PSF 阶段检查清单

### 启动前
- [ ] PRD 初稿完成，核心场景明确
- [ ] Story 拆分完成，优先级排好
- [ ] 工具链就绪（飞书看板、代码仓库）
- [ ] 验证用户名单确定

### 每个 Sprint
- [ ] Sprint Planning 完成，Backlog 明确
- [ ] Daily Standup 同步（异步即可）
- [ ] Developer 自测通过
- [ ] PO 验收完成
- [ ] Sprint Review 演示并收集反馈
- [ ] Retrospective 复盘并记录改进项

### PSF 结束
- [ ] 所有 P0 Story 完成
- [ ] 至少 3 个用户完成验证
- [ ] 用户反馈整理完成
- [ ] PSF 验收报告输出
- [ ] PMF 阶段范围和优先级确定
