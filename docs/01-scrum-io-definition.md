# Scrum 各阶段输入输出定义

> 版本：v1.0 | 日期：2026-08-26
> 适用：SecureTrans 项目所有迭代（PSF/PMF/Scale 阶段通用）
> 原则：轻量敏捷，聚焦关键交付物，不搞形式主义

---

## 一、Scrum 迭代全景

```
┌─────────────────────────────────────────────────────────────────┐
│                        Sprint（1-2周）                            │
│                                                                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐       │
│  │  需求阶段  │─▶│  设计阶段  │─▶│  开发阶段  │─▶│  测试阶段  │       │
│  │ Planning │  │  Design  │  │   Dev    │  │   Test   │       │
│  └──────────┘  └──────────┘  └──────────┘  └────┬─────┘       │
│                                                     │             │
│  ┌──────────┐  ┌──────────┐                       │             │
│  │  复盘阶段  │◀─│  验证阶段  │◀──────────────────────┘             │
│  │ Retro    │  │  Review  │                                     │
│  └──────────┘  └──────────┘                                     │
└─────────────────────────────────────────────────────────────────┘
```

## 二、各阶段详细输入输出

### 阶段 1：需求（Planning / Backlog Refinement）

**时间**：Sprint 第 1 天，1-2 小时

**核心活动**：
- PO 讲解本 Sprint 目标和优先级
- 团队拆分 Story，估算工作量
- 确认验收标准（DoD - Definition of Done）
- 识别依赖和风险

**输入**：

| 输入项 | 来源 | 说明 |
|--------|------|------|
| 产品 Backlog | 飞书多维表格/Gitea Issues | 按优先级排序的 Story 列表 |
| 上一个 Sprint 复盘结论 | 复盘文档 | 未完成项、改进项、技术债 |
| 用户反馈 | 用户验证记录 | 新需求、Bug、体验问题 |
| Lean Startup 阶段目标 | 阶段映射文档 | 当前大阶段的核心验证目标 |

**输出**：

| 输出项 | 格式 | 说明 |
|--------|------|------|
| Sprint Backlog | Gitea Issues + 里程碑 | 本 Sprint 要完成的 Story 列表 |
| Sprint 目标 | 1句话 | 本 Sprint 要达成的业务目标 |
| Story 验收标准 | 每个 Issue 的描述 | 可验证的行为清单 |
| 工作量估算 | Story Points / 人天 | 每个 Story 的估算 |

**Story 模板**（简化版）：
```
标题：[P0/P1/P2] 作为[角色]，我可以[功能]，以便[价值]

验收标准：
1. [具体可验证行为1]
2. [具体可验证行为2]
3. [具体可验证行为3]

估算：XS/S/M/L
依赖：无 / [其他Story]
```

**质量门**：
- ✅ 每个 Story 都有明确的验收标准
- ✅ 总工作量不超过团队容量的 80%（留 20% 给意外）
- ✅ P0 Story 全部纳入，P2 可选

---

### 阶段 2：设计（Design / Technical Design）

**时间**：Sprint 第 1-2 天，与开发并行

**核心活动**：
- 复杂 Story 的技术方案设计
- 接口定义（API 契约）
- 数据模型设计
- 架构决策记录（ADR）

**输入**：

| 输入项 | 来源 | 说明 |
|--------|------|------|
| Sprint Backlog | 需求阶段输出 | 本 Sprint 的 Story |
| PRD / 架构文档 | 项目文档 | 产品需求和技术约束 |
| 现有代码 | Git 仓库 | 当前实现状态 |

**输出**：

| 输出项 | 格式 | 说明 |
|--------|------|------|
| API 接口定义 | 代码注释 / 文档 | 请求/响应格式、状态码 |
| 数据模型变更 | SQL / 迁移脚本 | 表结构变更 |
| 架构决策记录 | docs/adr/ 目录 | 重大技术选型的决策理由 |
| 原型/UI 草图 | HTML / 截图 | 前端页面设计（如需要） |

**质量门**：
- ✅ P0 Story 的接口和数据模型已定义
- ✅ 重大技术选型有 ADR 记录
- ✅ 设计方案团队评审通过（口头即可）

> **PSF 阶段简化**：小功能可跳过正式设计，直接在代码中体现。只有架构级决策（如 os.rename vs 软链接、Flask vs FastAPI）需要 ADR。

---

### 阶段 3：开发（Development）

**时间**：Sprint 第 2-5 天（1周Sprint）或第 2-8 天（2周Sprint）

**核心活动**：
- 编码实现
- 单元测试（核心逻辑）
- 代码自审
- 每日站会同步进度

**输入**：

| 输入项 | 来源 | 说明 |
|--------|------|------|
| 设计输出 | 设计阶段 | API定义、数据模型 |
| Story 验收标准 | Sprint Backlog | 要实现的行为 |
| 编码规范 | AGENTS.md / 项目约定 | 代码风格、目录结构 |

**输出**：

| 输出项 | 格式 | 说明 |
|--------|------|------|
| 功能代码 | Git 提交 | 实现 Story 的代码 |
| 单元测试 | test_*.py | 核心逻辑测试覆盖 |
| API 测试用例 | test_api.py | 端到端接口测试 |
| 代码提交记录 | Git log | 每个 Story 对应清晰的 commit |

**Git 提交规范**：
```
<type>(<scope>): <subject>

type: feat(新功能) / fix(Bug修复) / docs(文档) / refactor(重构) / test(测试) / chore(构建/工具)
scope: 模块名（auth / submission / approval / admin / deploy / doc）
subject: 简短描述（不超过50字）

示例：
feat(submission): 实现文件流式上传和MD5计算
fix(auth): 修复gunicorn启动时数据库不初始化的问题
docs(deploy): 补充封闭数据中心部署指南
```

**分支策略**（轻量级）：
```
main ──────────────────────────────── 稳定分支，始终可部署
  └─ sprint-1 ──────────────────── Sprint 开发分支
       ├─ feat-upload-file        功能分支（可选，大功能用）
       └─ fix-auth-bug
```

> **PSF 阶段简化**：单人开发可直接在 main 分支提交，不搞复杂分支。多人协作时用 sprint 分支。

**质量门**：
- ✅ 代码通过本地测试（test_api.py 全通过）
- ✅ 无硬编码密码/密钥（用 .env 配置）
- ✅ 核心逻辑有测试覆盖
- ✅ 提交信息清晰可追溯

---

### 阶段 4：测试（Testing / QA）

**时间**：Sprint 最后 1-2 天

**核心活动**：
- 全量回归测试（test_api.py）
- 多角色权限验证
- 边界场景测试
- Bug 修复

**输入**：

| 输入项 | 来源 | 说明 |
|--------|------|------|
| 开发完成的代码 | Git 仓库 | 本 Sprint 实现的功能 |
| 测试用例文档 | SecureTrans_测试用例_v1.0.md | 15个测试场景 |
| 自动化测试脚本 | test_api.py | 35项API测试 |

**输出**：

| 输出项 | 格式 | 说明 |
|--------|------|------|
| 测试报告 | docs/test-report-sprint-N.md | 测试结果、通过率、Bug清单 |
| Bug 修复记录 | Git commit / Gitea Issues | 发现的Bug及修复状态 |
| 测试通过确认 | PO 签字/确认 | 核心流程验收通过 |

**测试层级**：

| 层级 | 内容 | 工具 | 执行时机 |
|------|------|------|---------|
| L1 单元测试 | 核心函数（MD5、特征码匹配、免审批判定） | pytest | 开发时 |
| L2 API测试 | 所有接口端到端测试 | test_api.py (urllib) | 测试阶段 |
| L3 场景测试 | 15个业务场景（P0/P1/P2） | 手动 + 自动化 | 测试阶段 |
| L4 探索测试 | 边界、异常、权限绕过 | 手动 | PO验收前 |

**质量门**：
- ✅ P0 测试用例 100% 通过
- ✅ 核心流程（提交→审批→摆渡→下载）端到端跑通
- ✅ 无 P0/P1 未修复 Bug
- ✅ 权限隔离验证通过

---

### 阶段 5：验证（Review / Sprint Review）

**时间**：Sprint 最后 1 天，30-60 分钟

**核心活动**：
- 演示本 Sprint 成果
- PO 对照验收标准逐条确认
- 收集反馈（内部团队 + 潜在用户）
- 更新产品 Backlog

**输入**：

| 输入项 | 来源 | 说明 |
|--------|------|------|
| 测试通过的功能 | 测试阶段输出 | 可演示的功能 |
| Story 验收标准 | Sprint Backlog | 验收依据 |
| 用户反馈 | 用户体验记录 | 外部视角 |

**输出**：

| 输出项 | 格式 | 说明 |
|--------|------|------|
| Sprint 验收结论 | 会议纪要 / 文档 | 哪些通过、哪些不通过 |
| 反馈清单 | Gitea Issues / 飞书任务 | 新需求、Bug、改进建议 |
| Backlog 更新 | 产品 Backlog | 优先级调整、新增Story |
| 演示记录 | 截图 / 录屏 | 成果展示（可选） |

**质量门**：
- ✅ PO 确认本 Sprint 目标达成
- ✅ 未完成项已移到下一个 Sprint 或 Backlog
- ✅ 反馈已记录并分类

---

### 阶段 6：复盘（Retrospective）

**时间**：Sprint 最后 1 天，Review 之后，30 分钟

**核心活动**：
- 回顾本 Sprint 做得好的、不好的、改进点
- 识别流程问题和技术债
- 制定下一个 Sprint 的改进行动

**输入**：

| 输入项 | 来源 | 说明 |
|--------|------|------|
| Sprint 执行数据 | Git log / 测试报告 | 实际工作量、Bug数、通过率 |
| 团队感受 | 团队成员 | 过程中的痛点和亮点 |
| 上一次复盘改进项 | 上次复盘文档 | 检查改进是否落地 |

**输出**：

| 输出项 | 格式 | 说明 |
|--------|------|------|
| 复盘文档 | docs/retro-sprint-N.md | 做得好/待改进/行动项 |
| 改进行动项 | Gitea Issues / 任务 | 下一个 Sprint 要落地的改进 |
| 技术债清单 | docs/tech-debt.md | 识别出的技术债及优先级 |

**复盘三个问题**（简化版）：
1. **做得好的**：哪些做法应该保持？
2. **做得不好的**：哪些问题需要改进？
3. **下一步行动**：下一个 Sprint 具体做什么改进？（不超过3条）

**质量门**：
- ✅ 改进行动项不超过 3 条（聚焦）
- ✅ 每条行动项有负责人和完成时间
- ✅ 上次复盘的改进项已检查落地情况

## 三、Sprint 节奏总表

### 1 周 Sprint（PSF 阶段推荐）

| 日期 | 活动 | 产出 |
|------|------|------|
| 周一上午 | Sprint Planning（需求） | Sprint Backlog |
| 周一下午 | 设计（复杂功能） | API定义/ADR |
| 周二-周四 | 开发 + 每日站会 | 功能代码 |
| 周五上午 | 测试 + Bug修复 | 测试报告 |
| 周五下午 | Review + 复盘 | 验收结论 + 复盘文档 |

### 2 周 Sprint（PMF 阶段推荐）

| 日期 | 活动 | 产出 |
|------|------|------|
| 第1周周一 | Sprint Planning | Sprint Backlog |
| 第1周周一-周二 | 设计 | API定义/ADR |
| 第1周周三-第2周周三 | 开发 + 每日站会 | 功能代码 |
| 第2周周四 | 代码冻结 + 测试 | 测试报告 |
| 第2周周五上午 | Bug修复 + PO验收 | 验收通过 |
| 第2周周五下午 | Review + 复盘 + 发布 | 复盘文档 + 发布包 |

## 四、Definition of Done（DoD）

一个 Story 算"完成"，必须同时满足：

- [ ] 代码开发完成，提交到 Git
- [ ] 核心逻辑有单元测试（如有）
- [ ] test_api.py 全量测试通过
- [ ] PO 对照验收标准确认通过
- [ ] 无 P0/P1 Bug
- [ ] 相关文档已更新（PRD/部署手册/用户手册，如需要）
- [ ] 代码可部署（部署脚本/配置已更新，如需要）
